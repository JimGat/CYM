# Development v3.0.38 — RF HAT ownership handoff

Development candidate only. Stable/main v3.0.37 and its accepted mixed-version
packages are unchanged. Seven release profiles and the two existing Development-only
profiles (Pancake-C5 DIY and WS-S3-5B) participate in this nine-profile build cycle.

## Contribution and integration

- Co-developer **@birolt29** supplied `rfhat-stale-nrf24-fix-v3.0.37.patch`
  (SHA-256 `2feed25709b2428c11eadadd5aa4e0ca172a75a8fef2edb0489b834b04c8cf30`).
  Retained intent: release stale nRF24 before IR/RF433/RFID/CC1101 claim, force a
  fresh nRF24 HW Test probe, and release both control pins after failed detection.
- Integration corrections by **JimGat**, not attributed to the supplied patch:
  also unwind both pins on SPI-device-add failure; request cancellation and wait
  at most 1.5 seconds for all five nRF24 worker owners before freeing/reusing the
  driver or transferring shared pins; explicitly refuse on timeout. This includes
  Channel Scan, Sniffer (including its final SD save), Futaba, the nRF24 worker and
  BLE Blaster's optional nRF24 worker. Worker completion is published after final
  context/radio access. Raw GPIO loopback and reentry use the same admission gate.
- A timeout displays a short **RF HAT busy** message; keep the previous ownership,
  allow the worker to finish, then retry. Never force-delete the worker or reuse its
  context/pins merely because the wait expired.
- GPIO8/9 describes the default C5 RF HAT mapping, not every board. Cleanup uses
  `RF_HAT_NRF24_CE_GPIO` / `RF_HAT_NRF24_CS_GPIO`; no board wiring, DIP routing,
  display/touch/SD transport, SPI clocks, USB/GPS ownership or layout is remapped.

## Evidence boundary

Focused regressions exercise the extracted production quiescence helper natively,
including each owner, cancellation, delayed completion, timeout and later retry.
Source contracts check failure unwinding, fresh probe and guarded claim call sites.
Full repository tests, all nine builds and independently verified packages are
publication gates, recorded separately; these checks are not RF/touch/SD hardware
qualification. No physical board was flashed by this cycle.

## Operator checks on the exact board and layout

1. Use the web flasher's **Development** channel and select the exact profile;
   never substitute generic CYD/HackerBox for CYD-2432S028-L or another board.
2. To preserve NVS, use matching-profile/layout Quick Flash (application only,
   `0x10000`), erase-all OFF. A merged full image at `0x0000` can overwrite NVS
   even with erase-all OFF. Do not use it as a settings-preserving update.
3. With the board powered down, set/connect the appropriate HAT and DIP routing.
   After boot, open nRF24 HW Test: a missing module must not remain cached Detected.
   Do not hot-switch hardware as a substitute for this safe power-off procedure.
4. Exit an active receive/scan screen, then enter another supported HAT tool.
   Expect either successful entry after the worker stops or **RF HAT busy** and
   safe retry. Confirm IR reception and touch behavior on your actual hardware,
   in both Classic and Modern layouts and both orientations.
5. Stop still preserves inspectable results; Home remains the release boundary.
   Repeat entry/Stop/Home/reentry and check serial logs, response and heap on hardware.
6. On Classic/HackerBox, USB Debug ON remains saved across reboot: keep GPS
   disconnected while ON; save OFF using Return normal / Reboot, then power off
   before reconnecting GPS. Other profiles keep diagnostics on their primary USB.

The reported GH #28 stale-pin explanation is source-level reasoning, not a new
independent physical reproduction or proof that every touch/IR fault has this cause.
