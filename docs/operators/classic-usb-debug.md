# Classic USB Debug operator instructions

The v3.0.33 persistent bounded-record path (with v3.0.34 routing/UI repairs) applies only to Classic CYD-2432S028 without PSRAM (neither board PSRAM nor SPIRAM enabled), explicitly excluding HackerBox Amberjack 0131 CYD. HackerBox and PSRAM profiles retain their prior volatile transport; C5/S3 consoles are unchanged. Hardware acceptance of this runtime option is NOT VERIFIED. Other boards retain their existing console behavior.

## Start logging

1. Physically unplug the GPS harness before enabling debug. A powered GPS TX can contend electrically with UART0 TX on GPIO1 even if firmware GPS is disabled. Disabling GPS in a menu is NOT sufficient. Disconnect other external drivers on that shared signal too.
2. Connect the verified board USB-to-UART bridge to your computer. Open its serial port at **115200 baud, 8 data bits, no parity, 1 stop bit, no hardware flow control**. Do not assert DTR/RTS or use an auto-reset monitor if you want to retain the acknowledged runtime session.
3. From either Classic or Modern Home, open Settings, Hardware Options, then the separate **Classic USB Debug** entry. Scroll the Hardware Options tile area if necessary, especially in landscape. The existing **Debug diagnostics** switch is verbosity, not this transport.
4. Read the warning and tap **I disconnected GPS - Enable**. Cancel / Close before acknowledgement leaves normal GPS and silent application logging unchanged. Expected status: ON, 115200 8N1, GPS unavailable. The serial stream starts with an application log containing `Classic USB Debug ON` (best effort); subsequent existing application logs are forwarded. No command prompt is provided.
5. For optional diagnostic measurements, enable **Debug diagnostics** separately in Hardware Options. On Classic without PSRAM, both settings persist independently: the acknowledged transport opt-in is stored as `cym_usb/enabled`. Keep GPS physically disconnected across every reset while USB Debug is saved ON. HackerBox retains volatile transport behavior. Returning with Back/Home or closing the popup preserves an already acknowledged active transport. Reopening Hardware Options shows the current mode. GPS Info explicitly reports GPS unavailable; old coordinates may remain last-known/stale, never a live fix.

Development v3.0.29 applies explicit opaque theme text, Montserrat 14 body text and contrasting CYM blue action buttons to this popup and its Hardware entry. Both the tile list and the bounded popup scroll in portrait (240x320) and landscape (320x240); scroll down to reach acknowledgement, Return normal / Reboot and Cancel / Close. The v3.0.33 warning explicitly explains persistence and the OFF-plus-reboot GPS boundary. Host LVGL framebuffer renders cover both palettes and orientations, including enabled/error status, but do not qualify a physical LCD. No new GPS task or serial REPL is started. C5/S3 native-console behavior is not changed.

## Return to normal GPS

1. Leave GPS physically unplugged. Open Classic USB Debug again and tap **Return normal / Reboot**.
2. On Classic without PSRAM, OFF must first be saved and committed in NVS. The firmware restores the previous log sink, detaches UART0 TX from GPIO1 and deletes its owned UART0 driver before rebooting. The next boot is normal, USB Debug OFF. GPS initialization is inhibited from the acknowledged attempt until that reboot, including failed enable attempts; it cannot restart into a partially removed log transport.
3. Power off before reconnecting GPS, then power on for normal GPS operation. This also avoids connecting GPS during reset-time ROM pin activity. Do not infer that an application shutdown can control ESP32 ROM behavior.
4. If enable, OFF save, or TX shutdown fails, the UI reports failure and leaves GPS inhibited. A failed TX shutdown does not reboot. Keep GPS disconnected. A power cycle does NOT clear a saved ON flag. Retry Return normal / Reboot until OFF is committed and shutdown succeeds; do not reconnect on an error. If NVS cannot be repaired, recover the setting while the harness remains disconnected. Re-entry after a failed attempt requires reboot/power cycle, not another acknowledgement. Repeated enable while already ON is idempotent.

## Logging limits and connector facts

- First enable requires the physical-disconnection acknowledgement. Subsequent Classic no-PSRAM boots restore that saved authorization immediately after successful NVS initialization and before GPS init/probes/reads. Logs begin at that point, including a best-effort numeric `reset_reason` record. Messages earlier in application startup are not replayed. ROM, bootloader, panic/backtrace and reset-time output do NOT pass through this runtime sink; it does not promise capture of the crash itself, retained logs or SD crash storage.
- `CONFIG_ESP_CONSOLE_NONE` and bootloader log level NONE remain unchanged. Normal OFF application logging does not use UART0. Original ESP32 ROM/reset/download activity is separate and not controlled by this application option. This is not native USB/JTAG.
- Classic bounded transport: 3072-byte FIFO queue, 1024-byte line assembly and 1024-byte format workspace, all in one enable-time allocation (plus indices/owner metadata). Maximum payload is 1022 bytes per newline-delimited record; a formatter invocation must produce at most 1023 bytes. Multipart IDF prefix/body/suffix calls are assembled before admission. Every admitted record ends in CRLF; an existing terminal CR is normalized. No per-log heap allocation or producer wait; no dedicated task/stack. A 5ms callback on the existing timer service attempts one FIFO write (the SDK takes its internal UART TX mutex; only this timer consumer calls it, never a producer) and retains zero/error/partial-write tails for retry.
- Queue saturation drops the entire newest completed record before any of it is sent. Overlong or failed formatting discards the pending record and conservatively ignores bytes through the next observed newline (which may drop an additional line). Oversized assembly similarly discards through newline. Busy/reentrant calls increment busy counters and poison pending assembly; the next successful caller discards through newline. Cross-task multipart ownership changes also discard rather than splice fragments. No unlimited/lossless guarantee is made. These are task-context application logs, not an ISR logger.
- In the v3.0.34 Classic candidate, the popup initializes its status/counters immediately above the scrolling warning, even while OFF. Its existing Hardware Options timer refreshes them while open; enable/OFF-save/TX-shutdown errors remain visible rather than being replaced by a success caption. It displays cumulative accepted-record, drop-event, busy-call and FIFO-retry counters (32-bit, since this boot). Drop events are conservative, not an exact count of lost original IDF messages. Open Hardware Options / Classic USB Debug to inspect them. Returning normal disarms producers immediately, discards software-pending bytes and releases TX; bytes already accepted by hardware cannot be retracted or guaranteed complete during shutdown/reset.
- OFF reserves no queue/workspace or dedicated stack. The static mutex, pointers and counters remain; UART RX driver storage and timer object are allocated only on enable and released on successful shutdown. Startup allocation/driver/timer/persistence errors leave the sink OFF and GPS inhibited. Clear-on-startup-failure is best effort: if NVS itself fails, saved ON may remain, so keep GPS disconnected across resets. OFF reports a persistence error rather than falsely claiming it cleared the key or rebooting. Invalid/unreadable saved ownership inhibits GPS with no TX for that boot.
- HackerBox/PSRAM profiles keep the prior 128-byte per-call buffer, 127-byte truncation and best-effort single FIFO write; this change does not silently extend persistence to them.
- The Guition V1.4 photo identifies **P1 VIN/TX/RX/GND**. The older V0.1 schematic connects P1 through 100 ohm signal resistors to UART0 GPIO1/GPIO3; that is not a continuity measurement of the V1.4 assembly. Normal CYM GPS instead receives through the GPIO matrix as UART2 RX GPIO1; nominal UART2 TX GPIO3 remains undriven. **P3 is GND/35/22/21.** Exact USB2 socket routing remains unverified: do not assume independent selectable USB sockets. GPIO22/27 remain reserved when RF-HAT is enabled.

## Required physical retest before acceptance

- On both Classic and HackerBox: normal cold boot, GPS absent/present, NMEA acquisition and sustained fix; verify application/bootloader silence separately from ROM behavior.
- Both Home layouts and both screen orientations: find entry, scroll full warning and every action, Cancel with no TX drive, acknowledge, close, Back/Home and re-enter with correct state. Watch for stale UI pointers or timers.
- With GPS disconnected, scope GPIO1 and capture bridge logs at 115200; verify no runtime TX before acknowledgement, bounded output under load, debug verbosity separate, and GPS consumers/status/rate/baud/detection blocked while active.
- Exercise persistent ON across reboot, explicit shutdown with committed OFF, reboot and OFF silence; scope TX release before restart and power off before reconnecting GPS. Repeat normal/enable/disable/reboot cycles, plus resource/setup failure paths where safely injectable.
- Previous Development v3.0.28 software gates passed: all eight board builds, 32 packaged artifacts, 708 unit tests (one expected skip) and 20 standalone regression runners. Compilation and host tests do not establish electrical safety, bridge routing, boot reliability, RF/SD coexistence or hardware acceptance.

## Development v3.0.29 verification

All eight board builds and 32 packaged artifacts passed verification. The final host suite passed 708 tests with one expected skip; 20 standalone regression runners passed. Production LVGL host renders reproduce the former dark-theme contrast failure and verify the corrected text/buttons in both themes and orientations. Physical LCD/touch and USB/GPS acceptance remain pending.

Use one cable at a time, preferably USB-C. This observation does not establish the exact net-level wiring or remove the physical GPS-disconnection requirement.

## v3.0.33 hardware diagnostic procedure (pending physical acceptance)

1. With GPS physically unplugged, open the bridge at 115200 8N1 using one USB cable. Enable Classic USB Debug from either Home layout. Expected: ON plus saved-across-reboot warning. Close/Back/Home must not disable it.
2. Reset without reconnecting GPS. Expected: application logs resume after NVS init; the reset-reason message is best effort. No ROM/bootloader/panic capture is claimed. GPS Info must remain unavailable.
3. Enable Debug diagnostics separately if needed. Reproduce the BLE scan warning and retain the actual serial capture, popup counters, reset reason and screen result. System-wide allocation pressure remains unresolved; do not interpret improved transport as a BLE fix.
4. Return normal / Reboot. Expected: OFF committed, TX detached, owned driver/timer/buffer released, then reboot. If the UI reports OFF-save/TX failure it must not reboot; keep GPS unplugged and retry. After a successful normal reboot, power off before reconnecting GPS; verify normal GPS reception separately.
5. Repeat in portrait/landscape and both navigation layouts. Verify responsiveness, electrical TX release, boot reliability and RF/SD coexistence on hardware. Host tests and packages alone are not acceptance.

## Development v3.0.34 Classic-only candidate

Scope: Classic CYD-2432S028 without PSRAM only, explicitly excluding HackerBox. C5, S3, HackerBox and PSRAM packages/settings are deliberately skipped and retain their prior versions. Classic firmware is built and packaged; 720 unit tests passed with one expected skip. Non-Classic packages remain byte-identical. No remote flash or hardware acceptance has occurred.

Production-code host tests reproduced two software defects: feature capture can install `dual_vprintf`, whose `rom_vprintf` fallback bypassed the bounded Classic sink; and the popup initialized counters only on a later timer tick, below its long safety warning. The fallback now uses the same opt-in bounded sink and stays silent while OFF. Counters initialize synchronously above the warning and refresh through the existing UI timer. The transport limits above remain unchanged. Earlier direct-sink tests did not exercise production hook replacement; earlier rendered-popup tests asserted styles and action reachability, not immediate counter content/viewport placement.

Neither reproduction establishes that the supplied serial capture took that path. In particular, the exact source of its 127-byte fragments and the BLE allocation/scanning failure remain unresolved. Generated Classic config, real main/transport preprocessing and linked code select the buffered path; package identity alone does not prove live execution. Do not diagnose a wrong/old flash from the fragment length, or treat this as a scanner fix.

Candidate operator procedure:

1. Keep GPS physically unplugged. Use one programming/debug cable, preferably the primary USB-C bridge, at 115200 8N1. This is a log stream, not a command console.
2. The candidate is v3.0.34, not a reflash of v3.0.33. Prefer application-only flashing at 0x10000 only if the installed Classic partition table matches the supplied table. Keep erase-all OFF. A merged full image can overwrite NVS; it is not settings-preserving merely because erase-all is OFF. Choose the exact Classic board and Development channel in the web flasher.
3. From Classic or Modern Home: Settings > Hardware Options > Classic USB Debug. The status at the top now includes Records / drops / busy / retries immediately; scroll the complete warning before acknowledging physical GPS disconnection. Enable USB Debug separately from Debug diagnostics verbosity. Expected status: ON, 115200, GPS unavailable, saved across reboot. Close/Back/Home preserves the mode. Reopening should show current counters immediately; counter increases depend on actual new logs.
4. With GPS still disconnected, exercise existing logging and a feature that enables its own log capture, then leave that feature and re-enter. Admitted long and multipart records must remain complete CRLF records; FIFO partial writes retain tails. Whole-record overload drops are counted, not lossless capture. Record the actual stream and LCD result; no fabricated sample output is supplied here.
5. Reset while saved ON. Application logging should restore after NVS and before GPS access; no ROM/bootloader/panic/crash capture guarantee. Debug diagnostics alone must not enable USB transport. Verify GPS Info remains unavailable.
6. Return normal / Reboot must commit OFF, release TX and reboot. If OFF-save or TX-shutdown fails, no reboot and a persistent error caption; keep GPS unplugged. Verify application silence after normal reboot, then power off before reconnecting GPS. Check normal GPS separately.
7. Repeat both layouts, light/dark themes and portrait/landscape. Physical readability, electrical safety, long-load responsiveness and RF/SD coexistence remain hardware-pending. Do not infer a BLE fix from clearer logs.
